# Plan: Compiled Discovery Cache

## Created
2026-06-10

## Status
ready

## Objective
Eliminate the per-request, full-codebase PHP-file scan in `Application::initialize()` by adding a CLI-compiled discovery cache: a `discovery:cache` command compiles attribute-marker discovery (preferences, plugins, observers, commands) into a generated `return [...]` PHP file that boot loads instead of rescanning, outside development.

## Discovery Notes

### What boot currently scans (verified)
All discovery runs inside `Application::initialize()` (called by `Application::create()` on every PHP-FPM request — there is no separate lazy `boot()`). The sequence (`packages/core/src/Application.php`):
1. `ModuleDiscovery` (`discoverInVendor`/`discoverInModules`/`discoverInApp`) + `DependencyResolver::resolve()` — reads each module's `composer.json` + optional `module.php`. Cost is O(modules), NOT the file-content bottleneck.
2. `discoverPreferences()` → `PreferenceDiscovery::discoverInModule()` — `findPhpFiles()` walks EVERY `.php` file in EVERY module `src/`, `file_get_contents` each, `str_contains('#[Preference')` pre-filter, then `extractClassName` + `loadClass` + reflection.
3. `discoverPlugins()` → `PluginDiscovery::discoverInModule()` — same full walk, `str_contains('#[Plugin')`.
4. `discoverObservers()` → `ObserverDiscovery::discover()` — same full walk, reflection for `#[Observer]` (no `str_contains` pre-filter — reflects every parseable class).
5. `discoverCommands()` → `CommandDiscovery::discover()` — same full walk for `#[Command]`.
6. `discoverRoutes()` → `RoutingBootstrapper` (only if `marko/routing` installed) — separate subsystem, closure/attribute heavy. OUT OF SCOPE (see below).

The O(all PHP files in every module) disk-IO + string-scan + reflection cost of steps 2–5 is the finding. It grows with every installed package and runs on every request.

### What is cacheable (verified value-object shapes)
The four discovery result types are flat `readonly` value objects of scalars/arrays — fully expressible as a literal PHP `return [...]` array and reconstructable without closures:
- `PreferenceRecord(string $replacement, string $replaces)`
- `PluginDefinition(string $pluginClass, string $targetClass, array $beforeMethods, array $afterMethods)` (arrays are `[methodName => ['pluginMethod' => string, 'sortOrder' => int]]`)
- `ObserverDefinition(string $observerClass, string $eventClass, int $priority, bool $async)`
- `CommandDefinition(string $commandClass, string $name, string $description, array $aliases)`

`ModuleManifest` is NOT cacheable: it carries `?Closure $boot` (and `string|Closure` bindings/singletons) from `module.php`, which cannot be serialized and which the framework forbids serializing. Module discovery therefore stays a live scan every request — but it only reads `composer.json` + `module.php` per module (O(modules)), not every PHP file, so it is not the bottleneck. The cache targets only the four O(all-files) marker scans.

### Cache file location & shape
- Location: `storage/cache/discovery.php`, relative to the project base (`ProjectPaths::$base`, default `getcwd()`). Matches the existing `storage/...` convention (`page-cache` config defaults to `storage/page-cache`). Path is overridable via the `DISCOVERY_CACHE_PATH` env var, read at boot by `DiscoveryEnvironment::cachePath()` (and mirrored in the shipped `config/discovery.php` as `cache_path` for `marko/config` consumers).
- Shape: a generated PHP file returning a nested array of pure scalars/arrays:
  ```php
  <?php
  // Generated by `discovery:cache`. Do not edit. Run `discovery:clear` to remove.
  return [
      'version' => 1,
      'preferences' => [ ['replacement' => '...', 'replaces' => '...'], ... ],
      'plugins'     => [ ['pluginClass' => '...', 'targetClass' => '...', 'beforeMethods' => [...], 'afterMethods' => [...]], ... ],
      'observers'   => [ ['observerClass' => '...', 'eventClass' => '...', 'priority' => 0, 'async' => false], ... ],
      'commands'    => [ ['commandClass' => '...', 'name' => '...', 'description' => '...', 'aliases' => [...]], ... ],
  ];
  ```
  `'version'` is a cache-format schema version so a future shape change invalidates stale files loudly rather than mis-hydrating.

### Dev-mode behavior
There is currently NO environment detection in core. This plan introduces it.

**CRITICAL CONSTRAINT (dependency direction).** `marko/core` is the lowest layer: it requires only `php` + `psr/container` and MUST NOT depend on `marko/config` (which itself `require`s `marko/core`). `ConfigRepositoryInterface` lives in `Marko\Config`, and it is bound lazily by `marko/config`'s `module.php` binding closure — a closure that itself resolves `ModuleRepositoryInterface` + `ProjectPaths` and only fires when something first requests `ConfigRepositoryInterface`. Module binding/boot callbacks run at the END of `Application::initialize()` (after all four discovery passes), so config is genuinely NOT available at discovery time. Therefore the BOOT-TIME cache gate cannot read `ConfigRepositoryInterface`.

**Resolution (two layers, different config sources):**
- **Boot-time gate** (Task 006, runs inside core's bootstrap, before `marko/config` is wired): reads environment DIRECTLY via a small core-owned reader (`DiscoveryEnvironment`) that consults `$_ENV` for `APP_ENV`, `DISCOVERY_CACHE_ENABLED`, `DISCOVERY_CACHE_PATH`. This is the bootstrap layer — the same layer where core already invokes `EnvLoader` and where the architecture doc explicitly sanctions reading `$_ENV['APP_ENV']` in `module.php` boot callbacks. Boot uses the cache only when `enabled === true` AND `environment !== 'development'` AND the cache file exists. `marko/core` gains NO dependency on `marko/config`.
- **`config/discovery.php`** (shipped defaults): still ships so that, WHEN `marko/config` is installed, the same values are visible/overridable through `ConfigRepositoryInterface` for the CLI commands (`discovery:cache`/`discovery:clear`), which run AFTER full boot when config IS available. The config file reads the same `$_ENV` keys, so the two layers agree.

In development the cache is always ignored (rescan) so adding/editing a `#[Plugin]` etc. takes effect immediately without recompiling. The cache file may still exist in development; it is simply not read.

### Corrupt-cache decision (loud errors)
When the cache is enabled and not in development and the file exists but is unreadable / not a PHP array / missing required keys / wrong `'version'`, boot throws a loud `DiscoveryCacheException` with a helpful message naming the path and instructing `vendor/bin/marko discovery:clear` (or recompile). It does NOT silently fall back to a filesystem scan in production — a corrupt cache is a deployment fault and must surface, per the loud-errors principle. (A missing file is NOT corrupt: it simply means "not compiled yet" → boot rescans normally.)

### Prerequisite (hard dependency)
This plan MUST land AFTER `tier2-high-correctness/003-classfileparser-tokenizer.md` (replacing the buggy `preg_match('/class\s+(\w+)/')` with a `token_get_all()` parser). That task's notes explicitly call this out: caching is only correct if the underlying scan is correct — otherwise the compiled cache permanently bakes in silently-skipped files. ## Scope

### In Scope
- `DiscoveryEnvironment` reader in `marko/core` (NO dependency on `marko/config`): reads `$_ENV` for `APP_ENV`, `DISCOVERY_CACHE_ENABLED`, `DISCOVERY_CACHE_PATH` and exposes `enabled()`, `environment()`, `cachePath()`. This is the boot-time gate's config source.
- `DiscoveryCache` service in `marko/core`: write/read/exists/clear the compiled `storage/cache/discovery.php` file; serialize the four discovery result arrays to a literal PHP file; hydrate them back into `PreferenceRecord` / `PluginDefinition` / `ObserverDefinition` / `CommandDefinition` objects; loud `DiscoveryCacheException` on corrupt/invalid/version-mismatched content.
- A `DiscoveryCompiler` that runs the four existing discovery passes over all modules and produces the plain-array payload (the data the command writes).
- `packages/core/config/discovery.php` shipped defaults reading the same env keys, so the values are visible/overridable through `ConfigRepositoryInterface` WHEN `marko/config` is installed (consumed only by the CLI commands, which run after full boot — core itself never reads it).
- Boot integration in `Application::initialize()`: when the cache is enabled and `environment !== 'development'` and a valid cache exists, hydrate preferences/plugins/observers/commands from `DiscoveryCache` instead of running the four scans; otherwise rescan. Corrupt cache → throw. The gate reads `DiscoveryEnvironment`, never `ConfigRepositoryInterface`.
- `discovery:cache` command (`#[Command]`): compile + write the cache file; report counts and path; exit non-zero with a helpful message on write failure.
- `discovery:clear` command (`#[Command]`): delete the cache file; succeed (idempotent) when already absent.

### Out of Scope
- Caching module discovery / `ModuleManifest` (carries closures — not serializable; and not the file-scan bottleneck).
- Caching routes (`RoutingBootstrapper` lives in `marko/routing`, is optional, and is closure/attribute heavy — a separate effort).
- An `optimize` umbrella command aggregating multiple caches (can wrap `discovery:cache` later).
- OPcache / autoloader-level optimizations.
- Auto-recompiling the cache on file change (a watcher) — development simply rescans.
- README/docs (handled by the post-implementation doc-updater pipeline).

## Architecture Notes
- **Dependency direction is the load-bearing constraint.** `marko/core` requires only `php` + `psr/container`. NOTHING added by this plan may import from `Marko\Config`. `ConfigRepositoryInterface` is forbidden in core's boot path. The env-reading at boot time is done by a core-owned `DiscoveryEnvironment` reading `$_ENV` directly (bootstrap layer — the same layer as `EnvLoader` and `module.php` boot callbacks, which the architecture doc explicitly allows to read `$_ENV['APP_ENV']`). The shipped `config/discovery.php` is for `marko/config` consumers (the CLI commands) only; core never loads it.
- Namespace: `Marko\Core\Discovery` for `DiscoveryCache`, `DiscoveryCompiler`, `DiscoveryEnvironment`; `Marko\Core\Exceptions` for `DiscoveryCacheException` (alongside existing core exceptions).
- `DiscoveryCache` depends on `ProjectPaths` (for base path) and `DiscoveryEnvironment` (for cache path); both via constructor promotion, `readonly` where appropriate. No `final`, no magic methods, no traits, strict types, full type declarations.
- `DiscoveryCompiler` reuses the EXISTING `PreferenceDiscovery`, `PluginDiscovery`, `ObserverDiscovery`, `CommandDiscovery` classes unchanged — it just collects their `array<...Definition>` output across the resolved module list and maps each value object to its array form. This guarantees cached output is byte-identical in meaning to a fresh scan (same classes, same code path).
- Serialization: write via a deterministic array literal (e.g. `var_export` of the payload wrapped in `<?php return ...;`) so the file is `opcache`-friendly and diff-stable. Hydration reconstructs the value objects by `new PreferenceRecord(...)` etc. — never `unserialize`, never closures.
- `DiscoveryEnvironment` is a plain core class (constructor-promoted, no external deps) whose getters read `$_ENV` LIVE at call time with the documented defaults (`enabled` → `DISCOVERY_CACHE_ENABLED`, default `true`; `environment` → `APP_ENV`, default `production`; `cachePath` → `DISCOVERY_CACHE_PATH`, default `storage/cache/discovery.php`). `enabled` coercion (production-safety): the case-insensitive values `0`, `false`, `no`, `off`, and empty disable; any other present value enables; absent defaults to enabled. NOTE: reading `$_ENV` directly in this class is the deliberate, sanctioned exception — it IS the config-translation layer for the bootstrap path, exactly like a `config/*.php` file, and core cannot reach `marko/config` here.
- The shipped `config/discovery.php` mirrors the `page-cache.php` style (`return [ 'enabled' => ..., 'environment' => ..., 'cache_path' => ... ]` reading the same `$_ENV` keys). It exists solely so `marko/config` consumers can see/override these values; the CLI commands MAY read it via `ConfigRepositoryInterface` since they run after full boot. Core's boot path does NOT read it.
- Boot integration computes `$useCache = $env->enabled() && $env->environment() !== 'development' && $cache->exists()` once (after `ProjectPaths` is registered at line 149), then forks PER SUBSYSTEM at the existing call sites — NOT one monolithic branch around all four. The existing interleaving must be preserved EXACTLY: preferences (157) → plugins (160) → observers (163) → [event-dispatcher + module-repository wiring, 166-171, unchanged] → commands (174). Each subsystem runs EITHER its `discoverX()` scan OR its `registerXFromCache()` hydration — the two halves are mutually exclusive (registering from both would double-register and `CommandRegistry` would throw `duplicateCommandName`). The `discoverCommands` registry/runner container wiring (binding `CommandRegistry`, creating `CommandRunner`) MUST still run on BOTH paths — only the SOURCE of the command DEFINITIONS changes, not the wiring. Keep `ModuleDiscovery`, autoloader registration, container/registry setup, binding registration, event-dispatcher creation, `discoverRoutes`, and module `boot` callbacks exactly as today.
- The gate runs during CLI boot too (`CliKernel::doRun()` calls `initialize()` before dispatching any command). `discovery:cache` recompiles correctly regardless (module list is always live; the compiler runs a fresh scan). A CORRUPT cache throws during `initialize()`, so `discovery:clear` cannot self-heal a corrupt boot — the recovery instruction is to delete the named file (the `DiscoveryCacheException` suggestion names the path first).
- Test isolation is a hard requirement (Tasks 001, 004, 006): `$_ENV` is process-global and Pest runs in parallel per worker, so every test mutating `APP_ENV`/`DISCOVERY_CACHE_ENABLED`/`DISCOVERY_CACHE_PATH` must snapshot+restore those keys, and every test writing a real cache file must use a unique per-test temp base and clean it up — otherwise the ~40 existing `Application::initialize()` tests silently flip onto the cache path.
- Commands follow the `ClearCommand`/`ListCommand` pattern: `readonly` class, `#[Command(name: 'discovery:cache'|'discovery:clear', description: ...)]`, implements `CommandInterface`, `execute(Input, Output): int`, dependencies injected (`DiscoveryCompiler`, `DiscoveryCache`). `Output` only exposes `write`/`writeLine` — use `writeLine` for all messaging; non-zero return for failure.

## Risks & Mitigations
- **Stale cache after deploy.** If a deploy adds packages/markers but the cache is not recompiled, boot would serve stale discovery. Mitigation: document that `discovery:cache` must run on deploy (release step); the `'version'` key guards against format drift; dev never reads the cache. (No mtime invalidation in this cut — explicit recompile is the contract.) Operator-intent footgun: `DISCOVERY_CACHE_ENABLED=no`/`off` now disables (wider false-set), matching the obvious expectation rather than silently staying enabled.
- **Corrupt cache bricks recovery via the CLI.** `initialize()` runs before any command dispatches, so a corrupt cache throws before `discovery:clear` can execute. Mitigation: the corrupt-cache exception names the file path to delete as the primary recovery; `discovery:clear` is documented (Task 005) as only working when boot succeeds; dev never reads the cache so dev boot is never blocked.
- **`$_ENV`/cache-file test leakage flips existing boot tests.** Mitigation: mandatory snapshot+restore of the three env keys and unique per-test temp bases with cleanup (Tasks 001, 004, 006).
- **Cache compiled against buggy parser.** Mitigated by the hard prerequisite on tier2 task 003 (tokenizer parser) — stated above; do not start before it merges.
- **`DiscoveryCompiler` must instantiate the same discovery classes the same way as `Application`.** `ObserverDiscovery`/`CommandDiscovery` take a `ClassFileParser`; `PreferenceDiscovery`/`PluginDiscovery` are `new`-ed per module. The compiler must mirror `Application`'s construction exactly so cached output equals scanned output. NOTE: `Application` resolves `ObserverDiscovery` via `$this->container->get(ObserverDiscovery::class)` (autowired), while `CommandDiscovery` is `new CommandDiscovery($this->classFileParser)`. Since both only need a `ClassFileParser` (no preferences/plugins applied to discovery classes), the compiler may `new` all four directly — covered by an equivalence test (Task 003/006).
- **Closure-bearing `ModuleManifest`.** Explicitly NOT cached; module discovery stays live each request. The per-request module scan reads only each module's `composer.json` (+ optional `module.php`) — O(modules), NOT O(all PHP files) — so the perf win from caching the four file-content scans is preserved. Mitigation is the documented scope boundary.
- **Inverted-dependency trap (was the original plan's fatal flaw).** The first draft put a `DiscoveryConfig` wrapping `ConfigRepositoryInterface` into `marko/core` and read it during boot. That is impossible: core cannot require `marko/config`, and `ConfigRepositoryInterface` is not bound until module boot callbacks run (after discovery). Resolved by the `DiscoveryEnvironment` boot-time reader (no `marko/config` dependency). The shipped `config/discovery.php` is for `marko/config` consumers only.
- **First-ever `config/` dir in core.** `config/discovery.php` is harmless when `marko/config` is absent (core never reads it) and discoverable by `ConfigDiscovery` (globs `{modulePath}/config/*.php`) when present. The file basename is the top-level config key, so consumers read `discovery.enabled`/`discovery.environment`/`discovery.cache_path`. Task 001 does NOT assert it loads through `ConfigRepositoryInterface` (core tests must not depend on `marko/config`); it asserts the file returns the expected default shape.
- **Corrupt cache vs the recovery command (CLI boot trap).** `CliKernel::doRun()` calls `initialize()` before dispatching any command. A corrupt cache throws during `initialize()`, so `discovery:clear` cannot run through a corrupt boot. The corrupt-cache `DiscoveryCacheException` suggestion therefore names the FILE PATH to delete first (primary recovery), with `discovery:clear` as the convenience path once boot succeeds. The gate predicate excludes development, so a corrupt cache never blocks dev boot (it is never read in dev).
- **Test isolation / `$_ENV` leakage.** The gate reads `$_ENV`; the ~40 existing `Application::initialize()` tests would flip onto the cache path if a test leaks a mutated `APP_ENV`/`DISCOVERY_CACHE_ENABLED` or a leftover cache file. Snapshot+restore env keys and use unique per-test temp bases with cleanup (Tasks 001, 004, 006).
- **Schema-version constant single-sourcing.** The compiler (Task 003) must emit `'version' => DiscoveryCache::CACHE_VERSION`, never a literal, so a future bump invalidates stale caches loudly instead of producing fresh caches that fail their own version check.
- **Equivalence invariant.** The compiler `new`s the discovery classes while `Application` resolves `ObserverDiscovery` via the container; they agree only because no `#[Preference]` targets a discovery class. The compiler documents this bypass in a code comment, and Task 003's equivalence test guards it.
- **Write-failure surfacing.** `DiscoveryCache::write()` throws `DiscoveryCacheException::notWritable` (never returns false / never relies on a PHP warning) so `discovery:cache` can catch it and exit non-zero with a real message.
