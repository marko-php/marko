# Devil's Advocate Review: tier1-critical-security

Reviewed all 14 task files, `_plan.md`, the architecture/code-standards/testing docs, and cross-referenced every cited source seam against the actual `packages/` files. The plan was already vetted by the team; the Discovery Notes and line numbers are accurate. Findings below are the cracks that would surface mid-build, especially for parallel TDD workers who cannot coordinate.

## Critical (Must fix before building)

**C1 — Task 001 must declare the new methods `static`, or tasks 002/003 cannot call them the way the plan specifies.**
The existing `IdentifierValidator` API is entirely `static` (`isValidIdentifier()`, `assertNoDangerousPatterns()`, `parseSelectExpression()`), and tasks 002/003 call `IdentifierValidator::assertValidIdentifier()` / `::assertValidOperator()` / `::escapeDelimiter()` statically (`MySqlQueryBuilder` already calls `IdentifierValidator::isValidIdentifier()` and `IdentifierValidator::assertNoDangerousPatterns()` statically — verified at the `whereRaw` site). If task 001's worker implements them as instance methods, the driver-side calls in 002/003 will fatal. Task 001 does not currently state the methods must be `static`. This is a hard cross-task contract that must be pinned in task 001 so the three workers agree.

## Important (Should fix before building)

**I1 — Task 007 will silently break two existing `RateLimiterTest` assertions if the atomic rewrite is naive, and the task never says the existing suite must stay green.**
`packages/ratelimiter/tests/Unit/RateLimiterTest.php` already asserts exact behavior the rewrite must preserve:
- `it('reports too many attempts without incrementing')` (asserts the counter is exactly `3` after 3 `attempt()` calls and that `tooManyAttempts()` does NOT increment) — so `tooManyAttempts()` MUST stay a read-only `get()`, never `increment()`.
- `it('returns remaining attempts count')` expects `remaining()` = 2,1,0 across three attempts at limit 3 — so the atomic path must compute `remaining = max(0, maxAttempts - count)` where `count` is the value returned by `increment()`.
- `it('blocks when max attempts exceeded')` does 3 attempts then a 4th; with increment-first the 4th increments to 4 then blocks (`remaining` clamped to 0) — fine, but only if `remaining` is clamped.
Because increment-first means blocked requests keep growing the counter (the task acknowledges this for `retryAfter`), the worker must read `retryAfter` from the TTL via `getItem()` (not derive it from the count) AND must NOT regress these existing tests. Task 007 should explicitly require the existing `RateLimiterTest` to keep passing and call out `tooManyAttempts()`/`clear()` staying read-only.

**I2 — Task 014's claim that the unwrapped `FailedCommand` payload "must still expose `$data['class']`" is inaccurate and will mislead the worker.**
`FailedCommand::extractJobClass()` does `@unserialize($payload)` then checks `is_array($data) && isset($data['class'])`. But the stored payload is `Job::serialize()` = `serialize($this)`, which serializes an **object**, not an array with a `'class'` key — so `extractJobClass()` returns `'Unknown'` today for real jobs (verified against source). After `verifyAndUnwrap()`, the inner bytes are still the object serialization, so `$data['class']` is still absent. The task's note ("the wrapped payload must still expose that after unwrap") implies the worker should preserve an array-with-`class` shape that does not exist. Correct guidance: `FailedCommand` must `verifyAndUnwrap()` BEFORE `@unserialize()`, and the existing `'Unknown'` fallback behavior is preserved (do not invent a `class` key). The `FailedCommandTest` round-trip must be updated to wrap its fixture payload through `JobEnvelope`.

**I3 — Task 014 omits two test files that reference (un)serialize and will break.**
The task lists `JobTest`, `AsyncObserverJobTest`, `RetryCommandTest`, and the broker `*QueueTest` files, but a grep of `packages/queue/tests` shows `FailedCommandTest.php` and `Feature/IntegrationTest.php` also reference serialize/unserialize round-trips. Both will fail once payloads become signed envelopes. Add them to task 014's "tests MUST be updated" list (the IntegrationTest is likely a real-broker `@group integration` test — note it may need the signer wired through the integration harness, not just a unit fixture).

**I4 — Tasks 013 and 014 need the `marko/encryption` config present in the test bootstrap, or the signer can't resolve the key; the tasks don't say how the test seeds it.**
`EncryptionConfig::key()` calls `$config->getString('encryption.key')`, which **throws `ConfigNotFoundException` if the key is entirely absent from config** (it only returns `''` when `encryption.php` is loaded with `ENCRYPTION_KEY` unset). In an isolated `marko/cache-redis` or `marko/queue` unit test, `encryption.key` may not be registered at all. The tasks should specify that the signer depends on `EncryptionConfig` (or `ConfigRepositoryInterface`) and that tests construct it with a `FakeConfigRepository(['encryption.key' => '<test-key>'])` (flat dot-notation, per the `marko/testing` convention) — giving deterministic control over both the populated-key and empty-key (`''`) test cases. Without this the "throws loudly when the signing key is empty" test and the happy-path round-trip tests can't be written reliably.

**I5 — Task 014's constructor changes to `Worker`, `DatabaseQueue`, and `RabbitmqQueue` are real DI-seam edits that must update their `module.php` bindings AND every test that constructs them directly.**
- `Worker` (`packages/queue/src/Worker.php`) takes `(QueueInterface, FailedJobRepositoryInterface, QueueConfig)`; adding `JobEnvelope` is a new required param. `Worker` is autowired today, so the binding is fine, but any test that does `new Worker(...)` must add the signer.
- `DatabaseQueue` takes `(ConnectionInterface, string $table = 'jobs', string $defaultQueue = 'default')`. VERIFIED: `queue-database/module.php` uses a SIMPLE class-mapping binding (`QueueInterface::class => DatabaseQueue::class`), so the container autowires it and fills the two strings from their constructor defaults. Adding `JobEnvelope` (a container-resolvable type) keeps it autowirable — no `module.php` change needed — but `JobEnvelope` MUST be placed BEFORE the defaulted string params (a required param cannot follow an optional one in PHP).
- `RabbitmqQueue` takes `(RabbitmqConnection, ExchangeConfig, string $defaultQueue = 'default')` — same simple binding, same ordering rule.
Task 014 should call out: (a) put `JobEnvelope` ahead of any defaulted string param, (b) no `module.php` binding change is required (simple bindings autowire the new dependency), and (c) update direct-construction test setups in the broker test suites.

**I6 — Task 011 removes two `readonly` constructor params from `AdminAuthMiddleware`; confirm no `module.php` closure binding passes them.**
Verified the only construction site passing `controller`/`action` is the test helper `createMiddleware()` in `AdminAuthMiddlewareTest.php:73` (task 011 already flags rewriting it). Every production usage is `#[Middleware(AdminAuthMiddleware::class)]` (class-string, autowired). There is no `admin-auth/module.php` closure passing the two params, so removal is safe — but the task should add a one-line confirmation that the middleware is autowired (no module.php binding references the removed params) so the worker doesn't hunt for a phantom binding.

## Minor (Nice to address)

**M1 — Task 006's `withRoute()` adds two new readonly promoted params to `Request`; confirm `clone(... with ...)` preserves the existing four.**
`Request` currently promotes `(array $server, array $query, array $post, string $body)`. Adding `?string $controller = null, ?string $action = null` keeps `fromGlobals()` and all `new Request(...)` call sites valid (defaults). The PHP 8.5 `clone($this, ['controller' => ..., 'action' => ...])` form is cleanest and the task already mentions it — just ensure `server/query/post/body` are carried through (they are, since clone copies all properties). No change required; flagged for the worker's attention.

**M2 — Task 002/003: validating the operator at the storage method (`where`/`orWhere`/`join`) adds a `throw` to those methods, which currently have no `@throws`.**
Per code-standards "every method that contains a throw … MUST have a `@throws` tag," the worker must add `@throws InvalidColumnException` to `where()`/`orWhere()`/`join()`/`leftJoin()`/`rightJoin()`/`orderBy()`/`whereIn()`/`whereNull()`/`whereNotNull()`/`table()`/`count()`/`insert()`/`update()`. Not a blocker (lint catches it), but worth pre-stating so the worker doesn't get a surprise PHPCS failure.

**M3 — Task 012: `cache-file` keeps object support, so a tampered file that serializes a malicious object still deserializes in the general file cache.** This is the locked, documented trust-boundary decision (filesystem write = already RCE), but it means the F6 success criterion "all object-injection sinks closed" is intentionally NOT met for `cache-file`. Worth surfacing to the team that this is a deliberate residual, not an oversight, in case a stricter posture (HMAC-wrap the file cache value, currently out of scope) is later desired.

## Questions for the Team

**Q1 — Trusted-proxy resolution strategy (task 007):** the task correctly warns that "left-most XFF entry" is unsafe and offers two strategies (right-most-untrusted-hop vs. explicit trusted-proxy count). Which is the locked choice? The right-most-untrusted-hop walk is more robust for unknown chain depth; the count is simpler but brittle if the proxy topology changes. A human should pick one so the test (`it resolves the right-most untrusted hop`) matches the implementation.

**Q2 — Empty-key posture in dev (tasks 013/014):** the signer throws loudly when `encryption.key` is `''`. That is correct for "no silent unsigned fallback," but it means any dev running the Redis cache or database/rabbitmq queue without setting `ENCRYPTION_KEY` gets a hard failure on first read/write. Is a documented "you must set `ENCRYPTION_KEY` to use these backends" the intended DX, or should the failure message specifically name the env var and the affected backend? (Recommend the latter for the suggestion line.)

**Q3 — `AsyncObserverJob` wrapping approach (task 014):** the task offers two options (wrap `eventData` at construction vs. pass the signer into `handle()` via the existing `?callable $resolver` seam). Since `AsyncObserverJob` is built by application code that dispatches async observers, wrapping at construction requires the dispatcher to hold the signer. A human should confirm where async observers are dispatched from and whether that call site is container-managed, so the chosen approach is actually wireable end-to-end.
